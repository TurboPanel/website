# Sealed Secrets

The control plane sends your servers secrets: database passwords, an app's secret settings, Hosting Account passwords. This page explains, in plain words, how those secrets will stay private on the way, whatever sits between the two ends. It is not a key, a setting or a procedure: there is nothing here to copy or type.

<Callout type="info" title="Where this stands today">
  Sealed secrets are being built and are not in the current release yet. Today a secret on its way
  to a server is protected only by the padlocked connection (HTTPS), as described in [Daemon trust
  model](/docs/security/daemon-trust-model#connectivity). Everything from step 2 on is marked
  **Coming soon**. Nothing on this page changes how you deploy or what you type.
</Callout>

This is about keeping a secret private. Proving who sent the order it travels in is a different job, done by the control plane's key: see [Control Plane Identity](/docs/security/control-plane-identity).

## 1. The Problem

Secrets travel inside orders: "here is the database password", "set this app setting", "create this Hosting Account with this password". Today they are protected only by the padlocked connection.

<TrustDiagram name="sealedProblem" />

Behind a tunnel or a proxy (a Cloudflare tunnel in front of a self-hosted control plane, for example) the padlocked connection is opened in the middle and a new one is made to the server. Whoever runs the middle, or anyone who took over your web address, could read the secret as it passes. The padlocked connection stays on in everything below; the padlock in the next steps is added on top of it, not instead of it.

## 2. Each Server Has Its Own Padlock

Each server will make a **padlock** and keep the only **key**. It will give the control plane the **open padlock**: anyone can snap it shut, but only that server can open it again.

<TrustDiagram name="sealedPadlock" />

The server signs the hand-over with [its own key](/docs/security/daemon-trust-model), so nobody in the middle can swap in a padlock of their own. The key never leaves the server. You never see it or type it.

## 3. Secrets Travel in a Locked Box

The control plane will snap that server's padlock shut on every secret it sends. The tunnel, the proxy or an impostor at your web address sees only a locked box.

<TrustDiagram name="sealedBox" />

Only the server that made the padlock has the key, so only that server can open the box. A box locked for one server is useless on any other server, and useless to anyone in the middle.

## 4. The Other Way Too

Sometimes a server sends a secret **up**, for example the private part of a certificate it just obtained. The control plane will have its own padlock for that, published so every server can fetch it, and only the control plane can open what is locked with it.

## Stamp and Padlock

Two things travel with an order, and they do different jobs.

| Piece                                                                        | Job                                                  |
| ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| **Stamp** (the [control plane's key](/docs/security/control-plane-identity)) | Proves an order really came from your control plane  |
| **Padlock** (this page)                                                      | Keeps the secret inside the order private on the way |

The stamp proves who sent it. The padlock makes sure nobody else can read it.

## Who Holds What

| Thing                                | Kind   | Where it lives                                          | You do  |
| ------------------------------------ | ------ | ------------------------------------------------------- | ------- |
| **A server's key**                   | secret | On that server only                                     | Nothing |
| **A server's open padlock**          | public | On the control plane, one per server                    | Nothing |
| **The control plane's key**          | secret | Inside the control plane only                           | Nothing |
| **The control plane's open padlock** | public | Published by the control plane; every server fetches it | Nothing |

## Not Covered Yet

These are the gaps in the first release of sealed secrets, so you can judge them for yourself.

- **The control plane's padlock is checked over HTTPS only** until the install command carries the control plane's fingerprint (see [Control Plane Identity](/docs/security/control-plane-identity)). For secrets a server sends up, that stops someone who only watches the traffic, not someone who actively hijacks your web address. A server's own padlock is already safe, because the server signs it.
- **Hosting Account passwords** still travel unlocked on one path. They are sent scrambled, not as the real password.
- **A server on an older daemon** keeps getting unlocked secrets until it updates.
- **A connection that stays open across a control plane update** stays unlocked until it reconnects.

## In Short

Every secret will travel in a box locked with the receiver's padlock, so only the receiver can open it, whatever sits in the middle. Each server keeps its own key; the control plane keeps its own. You do nothing and save nothing.
