# Server metrics operations

Host/server metrics are a **core** control-plane feature — always on, **disposable**, and stored outside Postgres. There is no enable/disable switch. For the wire contract, metric list, backend mappings, and the dated Cloudflare cost model, see [Server metrics architecture](/docs/architecture/server-metrics).

## Configuration

| Variable | Default | Purpose |
| -------- | ------- | ------- |
| `TURBOPANEL_SERVER_METRICS_RETENTION_DAYS` | `90` | Retention in days — applies to both hot DuckDB rows and sealed Parquet partitions |
| `TURBOPANEL_SERVER_METRICS_DUCKDB_THREADS` | `2` | DuckDB `SET threads` cap |
| `TURBOPANEL_SERVER_METRICS_DUCKDB_MEMORY_LIMIT` | `128` | DuckDB `SET memory_limit` in MiB |
| `TURBOPANEL_METRICS_DIR` | `<stateDir>/metrics` | Metrics state root override (internal path — not required) |
| `CLOUDFLARE_ACCOUNT_ID` | — | **Workers only** — required for Analytics Engine SQL reads |
| `TURBOPANEL_ANALYTICS_ENGINE_API_TOKEN` | — | **Workers only** — Account Analytics Read token for AE SQL queries |
| `TURBOPANEL_SERVER_METRICS_AE_MAX_RANGE_SECONDS` | `7776000` (90 d) | **Workers only** — optional max query window override |

The self-hosted Deno path constructs `DuckDbParquetServerMetricsStore` directly against an internal path (`resolveMetricsDir()`), so it needs no operator-supplied credentials — it falls back to a temporary no-op store (with a one-time boot warning) only when the metrics directory cannot be created or opened.

**Workers (hosted):** add the `SERVER_METRICS` binding + `CLOUDFLARE_ACCOUNT_ID` + `TURBOPANEL_ANALYTICS_ENGINE_API_TOKEN` (Account Analytics Read) for chart queries. Missing either the account id or the token → soft `available: false` on reads, not a hard failure. Optionally tune the hosted query window with `TURBOPANEL_SERVER_METRICS_AE_MAX_RANGE_SECONDS`.

**Deno (self-hosted):** metrics persist to embedded DuckDB + Parquet automatically. Query failures return **503** `metrics_backend_unavailable`.

There is no analytics Ansible role — the daemon provisions nothing for metrics beyond the instance's own state directory; the instance creates and manages the DuckDB metrics directory itself on first use.

### Temperature display unit

Organizations set a display unit independent of storage: `GET`/`PUT /api/client/v1/organizations/:id/temperature-unit` accepts `"celsius"` or `"fahrenheit"` (default **celsius** when unset). This setting only changes how temperature charts render — every temperature metric is always **stored in Celsius**; conversion to Fahrenheit happens at render/query-response time, never at collection or storage.

## Hardware profile & sensors

The **hardware profile** (`server.metadata.hardwareProfile`, pushed to the daemon via the `metrics-sensor-overrides-update` cell command) is per-server operator configuration for which physical sensors and network interfaces feed the `sensors`-part metrics:

- **Sensor slot assignment** — CPU/GPU temperature and power, GPU utilization/fan, up to two disk temperatures, up to two ambient temperatures, board temperature, and up to three fan tachometers each resolve either by daemon auto-detection or an explicit operator override. There is **no auto-default for disk temperature** — an unassigned disk-temperature slot stays empty until an operator explicitly assigns it (or explicitly confirms "no sensor here" to suppress future auto-detection), unlike CPU/GPU sensors which auto-detect from hwmon out of the box.
- **`drivetempEnabled`** — the Linux `drivetemp` kernel module reads per-drive temperatures directly off SATA/SAS/NVMe drives, but probing it is intrusive enough (it can spin up idle drives) that it's off by default and requires explicit operator opt-in. Flipping it on fires a fire-and-forget `modprobe drivetemp` plus a `modules-load.d` drop-in so the module reloads across a host reboot; flipping it on again when it's already enabled is a no-op.
- **Hosting-path selection** — `hardwareProfile.hostingPath` overrides which filesystem the daemon probes for hosting-storage capacity; absent an override it falls back to the tenant principal home root.
- **NIC slot assignment** — `hardwareProfile.nic1`/`.nic2` name the interfaces reported as the named `nic1*`/`nic2*` rate metrics, resolved through the same hardware-profile round trip as the sensor slots.
- **`generation`** — bumps only when a sensor or NIC identity actually changes, and rides every sample as `hardwareProfileGeneration` so chart segmentation can tell a layout change apart from a plain value shift (see `generationBreaks` in the architecture doc).

A **virtualized host with no hwmon tree at all** simply never declares the `"sensors"` `MetricPart` — no charts render for that family, and this is expected behavior, not an error or a misconfiguration to chase down.

## Proxy traffic

Two independent, loopback-only sources feed the `traffic` metrics part — each resolves to `null` on its own if unreachable, and neither absence blocks the other:

- **Hosting Caddy metrics** — the `site-caddy` role's admin listener (`site_caddy_admin_addr`, `127.0.0.1:2039`) exposes Prometheus metrics at `/metrics` when the Caddyfile's global `metrics` option is set (`servers { metrics }` alone only turns on per-server instrumentation and does **not** expose `/metrics` — there is no supported way to run a second, metrics-only admin API). This is the **site** Caddy that fronts hosted tenant sites, not the separate hosting-ingress Caddy.
- **ProxySQL REST API** — a managed ProxySQL instance with `admin-restapi_enabled` turned on starts an unauthenticated `GET /metrics` REST server on `admin-restapi_port`, published to `127.0.0.1:6070` only — the same loopback-only posture as its admin MySQL-protocol port.

Both sources are opt-in only in the sense that they depend on whether those sidecars are actually running; there is no separate metrics-collection toggle. A server with neither sidecar running never declares the `"traffic"` part, same as a VM with no hardware sensors never declares `"sensors"`.

## Self-hosted schema upgrade

DuckDB has no in-place migration path for a breaking column-layout change. On every open, the self-hosted store decides whether to wipe from the actual store artifacts, not the sidecar `<metricsDir>/schema-version` marker alone:

- **No database file:** a fresh install — never wiped — unless a leftover pre-v3 `parquet/` tree survives from an old install, in which case that orphaned Parquet data is wiped so it can't union back into query results with mismatched columns.
- **An existing database file:** the marker is trusted outright when it already matches the current schema version. Otherwise the store probes the database's actual on-disk columns for the v3 marker columns (`probeSchemaIsCurrent`) rather than treating a missing or corrupt marker as proof of staleness — a **current** v3 database with a missing marker is preserved and opened untouched. Only a database whose probed schema is genuinely **not** current (or whose probe itself fails, e.g. a corrupt file) is wiped.

A wipe deletes `metrics.duckdb` (and its `.wal`) plus the whole `parquet/` tree together — a surviving old-schema Parquet partition would otherwise union back into query results with the new columns NULL-filled, silently corrupting aggregates. This is a **clean break with no v2 data retained**, consistent with the project's pre-MVP posture of never carrying old-schema data forward. The marker is written only after a fully successful open, so a crash mid-open retries the staleness check on next boot instead of trusting a half-built store.

## DuckDB + Parquet resources (self-hosted)

The self-hosted metrics store is **embedded in the instance process** — no container, no port, no separate daemon process, no credentials, and no analytics database service to install or monitor.

Everything lives under the metrics state root (`TURBOPANEL_METRICS_DIR`, default `<stateDir>/metrics`):

| Path | Role |
| ---- | ---- |
| `metrics.duckdb` | Hot database — recent samples and status events in typed tables |
| `parquet/server-metrics/year=YYYY/month=MM/day=DD/metrics.parquet` | Daily sealed archive — each completed UTC day exported out of the hot table |
| `tmp/` | DuckDB spill plus in-flight Parquet exports (swept on restart; never mistaken for sealed partitions) |
| `schema-version` | Sidecar marker driving wipe-on-stale (see above) |

Resource caps come from the env vars above: `TURBOPANEL_SERVER_METRICS_DUCKDB_THREADS` (default **2**) and `TURBOPANEL_SERVER_METRICS_DUCKDB_MEMORY_LIMIT` (default **128** MiB) bound the embedded engine's footprint.

## Retention

| Layer | Config | Default |
| ----- | ------ | ------- |
| DuckDB hot table + Parquet archive | `TURBOPANEL_SERVER_METRICS_RETENTION_DAYS` | **90** days |
| Analytics Engine (hosted) | Cloudflare platform | **3 months** — UI cannot exceed this on Workers |

The same daily archive tick prunes both expired Parquet partitions and any hot/status rows past the cutoff — change retention via env on the instance unit and it applies on the next tick.

## Troubleshooting ingestion

| Symptom | Likely cause | Action |
| ------- | ------------ | ------ |
| No samples at all | Metrics directory unusable (self-hosted) or AE not wired (Workers) | Check the instance boot log for the no-op store warning and verify the metrics directory is creatable; on Workers verify the AE binding + SQL credentials |
| API 503 on charts | DuckDB/filesystem error | Check the metrics directory is writable and the disk is not full; see instance logs for the underlying DuckDB error |
| Interrupted daily archive | Instance stopped mid-export | Nothing to do — the in-flight `.tmp` Parquet file is ignored and swept on the next tick, and the day is re-exported; hot rows are only deleted after the sealed file validates, so samples are never lost |
| Workers charts empty | AE SQL credentials missing | Set `CLOUDFLARE_ACCOUNT_ID` and `TURBOPANEL_ANALYTICS_ENGINE_API_TOKEN`; store reports `available: false` when either is absent |
| Workers charts 503 `metrics_backend_unavailable` | AE SQL API rejected the query or token | Token must be **Account → Account Analytics → Read**. Check Worker logs for `metrics queryHostSeries failed …` (includes the Cloudflare/SQL error). Confirm `CLOUDFLARE_ACCOUNT_ID` matches the TurboPanel account |
| Daemon connected, no metrics | Unsupported OS collector | Internal to `turbopaneld`: logs `metrics unsupported: unsupported_os:<os>`, stops periodic metrics for that attach, and does **not** send a metrics sample — check daemon logs |
| Gap after connect | Normal warm-up | First sample is immediate (gauges); rate metrics (CPU / disk / net) follow on the primed ~2 s snapshot |
| Sensors section missing entirely | Expected on VMs — not a bug | A host with no hwmon tree never declares the `"sensors"` part; there is nothing to configure and no error to chase |
| Disk-temperature slot showing nothing | No auto-default for disk temperature | An operator must explicitly assign the disk-temperature sensor slot (and enable `drivetempEnabled` if the drive needs the `drivetemp` module) via the hardware profile — it is never auto-detected the way CPU/GPU sensors are |
| Traffic charts missing | Caddy or ProxySQL sidecar not running, or its metrics endpoint unreachable | Each traffic source resolves independently — check the site Caddy admin listener (`127.0.0.1:2039`, global `metrics` option set) and the ProxySQL REST API (`admin-restapi_enabled`, `127.0.0.1:6070`) separately; one being down never blocks the other |

Writes are fire-and-forget at the ingest boundary — ingestion errors do not block daemon liveness.

## Troubleshooting missing charts (UI)

| Symptom | Likely cause |
| ------- | ------------ |
| "No metrics yet" | Daemon offline or still connecting (first sample is immediate; rates follow in ~2 s) |
| Storage still starting | DuckDB metrics directory not yet created (self-hosted) or AE binding/credentials (Workers) not ready yet — re-run instance-launch / converge |
| Unsupported OS | Server OS metadata from daemon hello (`server.os.family !== 'linux'`) — not a metrics wire signal; Linux collector failures appear as no data/gaps instead |
| Empty range | Selected window beyond retention (90 d API cap; 3 mo on hosted AE) |
| Backend unavailable | DuckDB 503 on self-hosted |
| Gaps in lines | `sampleCount` &lt; `expectedSampleCount` — missing samples, not zero usage |
| Stale appearance | Charts are not real-time below the ~60 s baseline collection interval |
| Sensors or traffic families absent from a chart's metric picker | Expected — those families are conditional parts; see the Troubleshooting ingestion table above |

Use `sampleCount`, `expectedSampleCount`, and `gapCount` from the series API — do not treat null/zero the same.

## Privacy

Metrics stores:

- **`serverId`** (authenticated UUID index) — from server context after auth, not client-supplied identity
- **Low-cardinality dimensions:** collection mode and `hardwareProfileGeneration` (the sensor/NIC layout epoch) — daemon version, OS name, architecture, kernel release, and resolved sensor/interface identities are **not** stored in metrics rows; they live in Postgres on the `server` row and the hardware-profile record instead

Metrics does **not** store organization names, account emails, hostnames, client IPs, license tokens, or secrets. Query endpoints require session + server read grant — never bare UUID access. (Internally, DuckDB stores missing values as plain SQL `NULL` columns while Analytics Engine uses a missing-value sentinel — a backend implementation detail with no user-facing impact.)
