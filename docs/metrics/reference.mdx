# Everything TurboPanel tracks

This is the complete list of what a TurboPanel server reports about itself: each reading, its unit, how often it is read, how long it is kept, and where you see it. The pages in this section explain how to **read** each chart. This page is the **inventory**.

<Callout type="info" title="Plain words">
  Names here are the ones you see in the web interface. Storage details (how readings are packed on disk or in the hosted store) are internal and are not documented.
</Callout>

## The rules that apply to everything [#rules]

| Topic | What happens today |
| ----- | ------------------ |
| **Reading rhythm** | The daemon reads the host and sends **one sample a minute**. The first sample after it connects goes out at once, and rates (CPU busy, disk and network speed) follow about two seconds later, once there are two readings to subtract. |
| **Live view** | While someone watches a short range, the daemon also sends a 10 second stream. The stream feeds the chart and is **not stored**; the minute sample is what history keeps. |
| **Slower readings** | A few readings are expensive, so they are refreshed less often and the latest value rides along with every minute sample. The refresh times are in the tables below and summed up in [How often each thing is read](#cadence). |
| **How long it is kept** | **TurboPanel High Availability** keeps about **3 months**. **Self-hosted** keeps **90 days** by default (`TURBOPANEL_SERVER_METRICS_RETENTION_DAYS`). Charts look back at most 90 days. Events and connection history are kept as long as the numbers. |
| **Where it is stored** | Each table has a **Kept on** column. **Both** means TurboPanel High Availability and Self-hosted keep the reading in history. **Self-hosted only** means the reading is recorded in history only on a self-hosted control plane; on TurboPanel High Availability it appears in the live view but is empty in history. |
| **Plans** | Every group on this page is collected on every plan, Docker included. A plan never switches a metric on or off. Because a server's box size sets how many network interfaces, drives, GPUs and extra filesystems are watched on TurboPanel High Availability, a server with more of them than that has the extra devices reported as unwatched. Self-hosted watches every device it finds. See [License tiers](/docs/deployment/tiers). |
| **Sizes** | Every minute sample carries the sizes its percentages are measured against ([below](#sizes)), so a resize or a memory balloon shows up as a step, not as a wrong percentage. |
| **Limits on a server** | A sample may carry at most **16 events**; the 16 most severe are kept and the daemon sends the rest in the next sample. A sample dated more than 5 minutes away from the control plane's clock, in either direction, is refused. |
| **Coming** | A stored-sample check (exactly one per minute per server), a limit of 120 events an hour, a tighter 60 second bound on samples dated in the future, and a 5 GiB cap on the self-hosted metrics store are written but not released yet. They are listed under [Coming](#coming). |

## What “Not reported” means [#not-reported]

A value is blank, never zero, when TurboPanel does not have it. Blank has four causes:

- **The host cannot measure it.** No swap, no GPU, no interrupt-pressure file in an older kernel, a virtual machine with no real sensors. The chart or the group is hidden or empty.
- **The daemon is older than the control plane.** A daemon that has not updated yet sends the plain sample, without the newer readings (OOM kills, container health, the sizes, host facts). They fill in once the daemon updates.
- **The reading was out of range.** A percentage is held between 0 and 100; any other impossible value (a negative size, for example) is stored as blank.
- **TurboPanel does not store it on purpose.** Nine readings are not stored on either store, to make room for the sizes. They show as no data everywhere, and each one can be worked out another way:

| Not stored | Get it another way |
| ---------- | ------------------ |
| Cores saturated | The top CPU process text names a hog; [CPU pressure](/docs/metrics/cpu#cpu-pressure) shows the effect. |
| Hosting free space | Free space on the disk that holds hosting ([Root filesystem available](/docs/metrics/storage#root-filesystem-bytes) or the extra filesystem that holds it). |
| Docker used space | Add the four Docker groups: image layers, container writable layers, volumes, build cache. |
| Logs used space | Not available. |
| Major page faults | [Memory pressure](/docs/metrics/memory#memory-pressure) is the better signal. |
| Unreclaimable kernel slab | Not available. |
| Caddy 2xx responses | Requests minus 4xx, minus 5xx. |
| Router backends up | Backends total minus the names of unhealthy backends. |
| Router requests | Caddy counts every request first. |

A reading can also be **Self-hosted only** in history (see the tables). That is different from the nine above: those are empty everywhere, these are only empty in TurboPanel High Availability history.

## Events [#events]

Events are things that happened at a moment: an out-of-memory kill, a disk fault, a network link going down, a GPU fault, the clock losing sync. TurboPanel has **38 kinds** in a fixed list. The full list with explanations is on [Metric events](/docs/metrics/events).

| Group | Kinds |
| ----- | ----- |
| Kernel and operating system | out-of-memory kill, hung task, connection-tracking table full |
| Filesystems | read-only, disappeared, remount |
| Disks and RAID | SMART critical, NVMe critical, NVMe media error, RAID degraded, rebuild started, completed, failed |
| Network and TurboFabric | link down, link up, flapping, mesh peer change, mesh unavailable, mesh recovered |
| Thermal, power and memory errors | fan fault, fan alarm, temperature alarm, temperature critical, power supply fault, voltage alarm, memory error corrected, memory error uncorrected |
| GPU | Xid fault, memory error, row remap, page retirement, fallen off the bus, thermal critical, disappeared |
| Clock and restarts | clock sync lost, clock sync restored, hardware list changed, boot count changed |

Checks run at different rhythms: most on every sample, hung tasks every 2 minutes, clock sync every 5 minutes, drive SMART every 10 minutes.

- **Kept:** as long as the numbers (about 3 months on TurboPanel High Availability, 90 days by default on Self-hosted).
- **Limit today:** at most 16 events per sample; over that, the 16 most severe are kept and the rest are held for the next sample.
- **Where:** the [Recent events](/docs/metrics/events) panel on the Metrics screen. The panel is left out when nothing happened in the range.
- Hardware-health events (the disk, thermal, power, memory and GPU groups) are on for physical servers by default.

## How often each thing is read [#cadence]

| Cadence | What |
| ------- | ---- |
| Every minute | CPU, memory, disk and network numbers, GPU, temperatures and power, pressure, Caddy, router and database proxy figures |
| Every 10 seconds (live view only, never stored) | The same numbers, while someone watches a short range |
| Every 30 seconds | Container health and totals |
| Every 2 minutes | Hung-task check |
| Every 5 minutes | Docker disk use, managed database count, clock-sync check, host text (software versions, load, top processes, largest sites) |
| Every 10 minutes | Drive SMART events |
| Every 15 minutes | Hosting, backup and log folder sizes |
| Every 30 minutes | Drive health text, database engine versions |
| Every 6 hours | Hosting certificate expiry |

A slower reading shows the same value for several minutes in a row. That is not a stuck chart.

## What shows on which screen [#screens]

| Screen | What it shows |
| ------ | ------------- |
| **Metrics** on a server | One chart per reading in the tables above, grouped as on this page, with a range from 5 minutes to 90 days. Gaps in a line are missing samples, not zero. |
| **Overview tiles** at the top of Metrics | The latest CPU utilization, memory used, hosting storage used, running and blocked tasks, and uptime. See [Server metrics](/docs/metrics#overview-tiles). |
| **Recent events** on Metrics | The events above, newest first. |

## Coming [#coming]

These are written but not released. This page will drop the label when they are.

- **Host health and About this host** in the web interface, and a chart for each health number that has none yet (OOM kills, interrupt pressure, process-limit use, root disk queue and operations, failed services, degraded RAID arrays, container health, containers' CPU and memory).
- **A host-facts route** that returns the newest facts, and facts recorded on Self-hosted.
- **Exactly one stored sample a minute per server**: a duplicate is refused, a sample sent too early is refused with a wait time.
- **120 events an hour per server**: events over the budget are dropped, most severe kept first, and the sample itself is still stored.
- **A 60 second bound on samples dated in the future.** Today the bound is 5 minutes either way.
- **A 5 GiB cap on the Self-hosted metrics store**; the oldest days are removed first.
