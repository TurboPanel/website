# Managed databases

A **managed database** is a database cluster TurboPanel provisions, secures and connects for you on your own servers: PostgreSQL, MySQL or MariaDB, in a container the platform owns, behind a shared listener that every consumer dials, with replication, promotion and backups handled from the app. You choose the engine, a version series and a server; the platform does the rest and hands you an endpoint and a first user. This chapter is written for the person creating and using one; the wiring underneath is in [Managed database ingress](/docs/architecture/managed-database-ingress).

## The model

A managed database is a **managed project** — one project whose environment holds a cluster instead of a compose stack. It has three parts:

- **The cluster** — one **primary** on the server you pick, plus any number of **replicas**. Engine containers are reachable only on the organization's private managed network; nothing publishes an engine port on the host.
- **The listener** — a shared ProxySQL on every server that hosts a member or a consumer, on a port the organization sets (`15432` for PostgreSQL, `13306` for the MySQL family by default). This is the only thing a client ever connects to. It routes each login to the primary or to read replicas, and it terminates client TLS with the organization's CA.
- **Logins and databases** — the users and databases you create on the **Data** tab. Each login carries a **connection role** that decides where the listener sends it.

Two facts shape everything below:

- **The version series is chosen once.** A cluster is created as PostgreSQL 18, MySQL 9.7 (the default) or 8.4, or MariaDB 11.8 (long-term support, the default) or 12.3, with a base-OS variant; the series never changes afterwards (`managed_series_immutable`). Only the variant may. MariaDB 12.3 can run on one server only for now: adding a replica, or converting a replica to a failover member, needs MariaDB 11.8 until failover for 12.x is supported. A 12.3 database that already exists keeps running as it is.
- **TLS between the listener and the engine is always on.** The **SSL mode** you set is a client-facing policy — whether the listener refuses a plaintext client and what verification the connection string tells the driver to do — never a switch for engine encryption.

## Before you begin

- A connected server with Docker; the cluster's primary runs there. Every server whose apps use a managed database runs the database proxy, and on a Raspberry Pi 5 running Raspberry Pi OS (Debian 13, "trixie") the default 16 KiB kernel cannot run it; one command switches the Pi to the 4 KiB kernel — see [Raspberry Pi and databases](/docs/using/raspberry-pi-and-databases).
- For a failover replica: a second server **in the same datacenter** as the primary. For a remote read replica: any server in the organization, with TurboFabric or a datacenter path to the primary.
- For a client on another server: that server enrolled in the organization (the listener is deployed to it when a service there binds the database).
- **Manage** rights on the organization.

### SSL modes

| Mode                | Plaintext client refused? | What the connection string tells the driver |
| ------------------- | ------------------------- | ------------------------------------------- |
| `disable`           | no                        | no TLS                                      |
| `allow`, `prefer`   | no                        | try TLS, fall back                          |
| `require` (default) | **yes**                   | TLS, no verification                        |
| `verify-ca`         | **yes**                   | TLS, verify the CA                          |
| `verify-full`       | **yes**                   | TLS, verify CA and hostname                 |

Resolution is three-layer — the cluster's own override, then the organization default (**Managed → Settings**), then the platform default `require`. Leaving a cluster on _inherit_ means an organization change applies to it later; setting a mode pins it.

A login's name must be unique across every cluster on servers the same organization owns — `username_in_use` if another cluster has it, `managed_user_exists` if this one does. `postgres`, `root`, `mysql` and `superadmin` are reserved.

## Name schemes

Every login and system user has two names: the **display name** you typed, and the **system name** the server or database engine actually sees (the _applied_ name). A **name scheme** decides how the second is made from the first. The control plane derives the system name; clients never supply it.

| Scheme              | System name                                                                                                                                              | Example           |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `plain`             | exactly what you typed                                                                                                                                   | `bob`             |
| `partial` (default) | what you typed, then `_` and 11 random lowercase letters and digits                                                                                      | `bob_x7k2m9qpz1a` |
| `random`            | 12 random characters: a leading letter, then 11 lowercase letters and digits. It never starts with a `tp` prefix and carries no trace of the typed name. | `u7k2m9x4qpz1`    |

The scheme applies to every kind of login or system user: Linux, SFTP and SSH system users, managed database logins (PostgreSQL, MySQL and MariaDB, within each engine's identifier limit), the managed admin login, and the replication login. The admin login is never `plain`: a `plain` request for it is applied as `partial`. System users declared in a compose document follow the organization default.

The typed name is at most 16 characters under `partial`, so the whole name stays within 28 characters. On the server each Linux user gets a group of the same name, so a name that matches a system or administrator group (such as `sudo`, `admin`, `wheel` or `staff`) is not allowed.

Three places choose a scheme:

- **Organization default.** An owner or manager sets it (default `partial`).
- **Per login or system user.** Each new login or system user can pick a scheme; it starts at the organization default.
- **Organization lock.** An owner or manager can force one scheme for every **new** login or system user. A request for a different scheme is refused with `principal_scheme_locked` (409). The lock can be turned off and on again.

Existing logins and system users are never renamed by a default or a lock change. The chosen scheme is stored on the login or system user (`options.nameScheme`). An organization that predates schemes keeps its old behaviour: randomized usernames on means `partial`, off means `plain`, and unset means `partial`.

**API.** `GET` and `PUT /organizations/:id/principal-defaults` read and write `{ nameScheme, schemeLocked }`. Creating a login or a managed user accepts an optional `nameScheme`; omit it to use the organization default.

## Replicas, promotion and disaster recovery

**Overview** tab — the topology.

| Replica class             | Where                          | What it is for                                                                                                            |
| ------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| **Failover replica**      | Same datacenter as the primary | Automatic failover when the primary dies; a **switchover** on demand.                                                     |
| **Remote / read replica** | Any server in the organization | Read traffic close to consumers, and **disaster recovery** when the primary's site is down. Never promoted automatically. |

MariaDB 12.3 stays on one server: **Add replica** and converting a replica to a failover member need MariaDB 11.8 until failover for 12.x is supported.

<Steps>
  <Step>
    **Add replica**, pick the class and the server, and whether it **serves read
    traffic** (`readEligible`). Apply.
  </Step>
  <Step>
    **Promote** a failover replica for a planned switchover: the old primary
    becomes a replica, the endpoint does not change.
  </Step>
  <Step>
    **Promote for disaster recovery** a remote replica only when the primary's
    site is gone: one writer results; any failover replica left in the old
    datacenter is rewritten to a read replica.
  </Step>
  <Step>
    **Remove** a replica that is no longer needed. The primary cannot be
    removed.
  </Step>
</Steps>

### Manual promote

**Promote** on a failover replica switches over: it asks the old primary to stop if its server is online, promotes the replica and points the endpoint at it, so the connection string does not change. The replica must be a **failover** replica that is streaming and no more than 64 MiB or 30 seconds behind on a **live** health read from its daemon (non-force promote always probes first; **Refresh health** on **Overview** updates stored readings but does not replace that probe). Over the API, `{ "force": true }` skips the lag and health checks (and accepts possible data loss) but never the replica class. A **read** replica can only be promoted with **Promote for disaster recovery**.

The old primary becomes a replica. If it could not be stopped, it is marked `needs_resync` and stays that way until you re-seed it from the new primary (`POST /environments/:id/managed/members/:memberId/resync`). **Promote** and disaster recovery keep going when the old primary or its server cannot be reached (the old member is marked **needs resync** afterward). Automatic failover on a **live** server is different: it must prove the old primary was drained and stopped first, or the journal records `unfenced` and nothing is promoted. Whole-host loss uses a separate attested fence — see [When the primary's server dies](#when-the-primarys-server-dies).

### Automatic failover [#automatic-failover]

When a primary dies, the platform can promote a same-datacenter **failover** replica on its own. The endpoint your applications dial does not change. Two detectors feed the same `beginAutomaticFailover` path (switch, 15 minute cooldown, candidate gate, command queue), but they fence the old primary differently:

| Path | What broke | How it is detected |
| ---- | ---------- | ------------------ |
| **Engine dead, host alive** | The database engine on a connected server | PostgreSQL: the daemon on the primary's server (`postgres-probe`, every 5 s, dead only after six consecutive hard failures spanning at least 20 s). MySQL and MariaDB: Orchestrator **DeadPrimary** on a live server (`managed-ha-event`). |
| **Host loss** | The primary's server is silent to the control plane | About once a minute, `ha-host-loss` on the control plane — see [When the primary's server dies](#when-the-primarys-server-dies). |

**Shared gates (both paths).** The report must name the cluster's current primary and come from a server in the same organization that hosts a member. `TURBOPANEL_AUTO_FAILOVER` must be on for this deployment (below). No automatic failover for this cluster may have **started** in the last 15 minutes. A same-datacenter **failover** replica must pass the candidate gate (stored health and/or an event-time **fresh-standby** probe — not only `streaming`; see the host-loss table). The control plane must be able to queue commands (`no_command_queue` otherwise).

**Engine-dead fencing (live host only).** The platform drains ProxySQL on the cluster, then stops the old primary container. Promotion runs only when drain and stop are confirmed. If the old primary's server is not connected, automatic failover does not send those commands: the row is `blocked` with `unfenced` because two writers would be possible. Host-loss automatic failover skips network drain/stop and uses an attested fence instead (`fenceBasis = host-loss-attested`, boot hold on the old host).

**Fresh-standby probe (engine dead).** When stored readings do not show a healthy streaming failover replica, the control plane probes each same-datacenter failover replica at event time. PostgreSQL may accept a non-`streaming` standby when its last streaming read is tied to the failure start (default 10 s margin), received WAL is replayed within 16 KiB, and the last receive lag was within 64 MiB; the replica that received the most WAL wins. MySQL and MariaDB require `fullyApplied === true` plus the same contact receipt; if more than one failover replica passes but their executed GTID sets differ, nothing is picked automatically — promote by hand.

**The switch.** `TURBOPANEL_AUTO_FAILOVER` is read when each event or host-loss decision runs. It accepts `on` or `off` (also `true`/`false` and `1`/`0`); any other value counts as off. Unset or blank: **on** everywhere except when `TURBOPANEL_ENVIRONMENT` is `staging` or `live` (**off** on those unless you set `on`). Self-hosted and TurboPanel High Availability **testing** and **canary** therefore default to on; **staging** and **live** default to off. Manual switchover and disaster recovery never read it. See [Control plane configuration](/docs/deployment/instance-configuration#runtime-services).

### Failover by scenario

Plain words for the three engines. MySQL and MariaDB share the same Orchestrator and GTID gates; only the detector label differs.

| Scenario | PostgreSQL | MySQL | MariaDB |
| -------- | ---------- | ----- | ------- |
| **(a) Engine dead, host alive** | **Can promote automatically** after the probe reports dead (~20 s minimum) plus gate time, when the switch is on, cooldown clear, command queue up, and a failover replica passes the candidate gate. **Fencing:** drain + stop on the live host before promote; **`unfenced`** if stop cannot be proved. **Force promote:** n/a (operator action) — **Promote** / `{ "force": true }` skips lag and health checks, not replica class; continues if the old primary cannot be stopped (**needs resync**). | Same automatic path via Orchestrator **DeadPrimary** on a live server; same fencing and **`unfenced`** rule on a live host. Fresh-standby: **`fullyApplied === true`**; split GTID sets block automatic pick. **Force promote:** same as Postgres. | Same as MySQL. |
| **(b) Host dead, control plane up** | **Can promote automatically** after the host is marked offline (`sweep_stale`), the host-loss window elapses (default **120 s**, `TURBOPANEL_HOST_LOSS_WINDOW_SECONDS`, clamped 60–300 s), peers corroborate silence, and the same switch/cooldown/queue/candidate gates pass — typically several minutes after the daemon last answered. **No** drain/stop on the dead host; **attested** fence (`host-loss-attested`) and **needs resync** on the old primary. Blocked codes include `fleet_outage`, `peer_streaming`, `not_corroborated`, `daemon_too_old`, `too_late` (after ~7.5 min from the offline mark). **Force promote:** **Promote** when automatic path is blocked or too slow. | Same host-loss path and timing; peer **`fullyApplied`** / GTID rules on the failover replica probe. **Force promote:** same as Postgres. | Same as MySQL. |
| **(c) Host alive, cut off from control plane** | Engine probe may still run locally, but if the daemon cannot reach the control plane the server is marked offline and **host-loss** may run. Automatic promotion is **refused** while any replica still reports **`streaming`** from the primary (`peer_streaming` — the host is probably up, only the control-plane link is down). **Force promote:** only after you accept split-brain risk — **Promote anyway** / `{ "force": true }`. | Same: **`peer_streaming`** blocks host-loss auto-failover; Orchestrator on other servers does not replace peer corroboration. **Force promote:** same as Postgres. | Same as MySQL. |
| **(d) Control plane down** | **No** automatic failover (no sweep, no `managed-ha-event` handling, no command queue). Daemons may still detect a dead engine locally; promotion waits until the control plane is back or you recover manually on another path. **Force promote:** unavailable until the control plane and replica daemon answer. | Same. | Same. |

**A `blocked` recovery row.** A refused automatic failover is recorded in the cluster's recovery history as a `blocked` row. Nothing was fenced or promoted, and the cause is in the row:

| Reason                   | Meaning                                                                                                                                | What to do                                                            |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `auto_failover_disabled` | The switch is off on this control plane.                                                                                               | Turn it on, or promote by hand.                                       |
| `cooldown`               | An automatic failover started less than 15 minutes ago. A refusal does not extend the cooldown, and the report is sent again after it. | Wait, or promote by hand.                                             |
| `unfenced`               | The old primary could not be confirmed stopped, so promoting would risk two writers.                                                   | Bring the old server back or confirm it is off, then promote by hand. |
| `no_command_queue`       | This control plane cannot send commands to servers.                                                                                    | A deployment fault; contact whoever runs the control plane.           |

A row can also be `blocked` because no same-datacenter failover replica was healthy enough to promote. A `blocked` row does not hold anything up: **Promote** and disaster recovery stay available.

## What to expect when a database fails over [#what-to-expect-when-a-database-fails-over]

Plain-words guide for the person on the **Overview** tab. Recovery history shows what the platform tried; the connection string your apps dial does not change after a successful switchover or automatic failover.

### After a switchover or automatic failover

The former primary is demoted to a replica. If its server was online, the platform stopped it cleanly first. If the stop could not be confirmed (the host was unreachable), the member stays **needs resync** on the topology — the app shows `needs resync` — and does not serve traffic until you fix it.

**What to do:** on that member, press **Resync** (two-step confirm: _Wipes this replica's data and re-seeds it from the primary._). The platform wipes its data directory and copies from the new primary. Any writes the old primary took while it was isolated are discarded and exist nowhere else. API: `POST /environments/:id/managed/members/:memberId/resync`.

### When the primary's server dies [#when-the-primarys-server-dies]

A dead database **process** on a live server triggers [automatic failover](#automatic-failover) through `postgres-probe` or Orchestrator. That path drains and stops the old primary on the connected host before promote; if drain/stop cannot be confirmed, the journal records `unfenced` and nothing is promoted. It does **not** run when only the host is silent — that is host-loss below.

A dead **server** is different: the engine-level detectors never run on a host that is not connected. About once a minute the control plane runs a **host-loss** sweep (`ha-host-loss`): it looks at how long the primary's server has been marked offline, whether the outage looks fleet-wide, and whether every other member's daemon corroborates that replication from the primary has stopped. **PostgreSQL, MySQL, and MariaDB** all use this path; `engine_unsupported` is only for engines outside that set (not something MySQL or MariaDB hit today).

**Fail closed until the silence is explained.** Inside the configured offline window (default 2 minutes, `TURBOPANEL_HOST_LOSS_WINDOW_SECONDS`, clamped to 60–300 seconds) the sweep waits. After the window, and only while the incident is still inside the decision cap (about 7.5 minutes after the offline mark), it may probe. It refuses when more than half of the organization's servers are offline (`fleet_outage`), when an operator reboot or daemon update on that server is still inside the planned grace (10 minutes), when the primary's daemon never advertised `managed-ha-boot-hold-v1` (`daemon_too_old`), when another member's server is offline or did not answer (`not_corroborated`), or when any probed replica still reports `streaming` from the primary (`peer_streaming` — the host is probably alive and only its link to the control plane is down). Past the decision cap it alerts only (`too_late`). After 30 minutes of silence the incident is dropped. Each refusal is a terminal `blocked` row with `metadata.detector = host-loss` and plain-words text (not the short codes above).

**When every peer corroborates**, the sweep calls the same automatic failover as an engine-dead report, with `hostLossIncident` set: the ordinary gates still apply (switch on, 15 minute cooldown, command queue, same-datacenter **failover** replica). The unreachable primary is not stopped over the network; it is marked **needs resync**, and the journal records an attested fence (`fenceBasis = host-loss-attested`, the boot hold is what stops it writing if the server returns). If the primary's server reconnects before promotion starts, the attempt ends as `blocked` with no cooldown extension.

| Engine             | How the failover replica is proven after host-loss                                                                                                                                                                                                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **PostgreSQL**     | Event-time health probes on same-datacenter failover replicas; the **fresh-standby** gate accepts a replica that is not `streaming` only when its last streaming read is tied to the failure start (10 second margin), received WAL is replayed within 16 KiB, and the last receive lag was within 64 MiB. Among several accepted standbys, the one that received the most WAL wins. |
| **MySQL, MariaDB** | Same probes and timing; the gate requires `fullyApplied === true` (every received transaction applied) plus the same contact receipt. If more than one failover replica passes but their executed GTID sets differ, automatic failover does not pick one — promote by hand.                                                                                                          |

**What to do when nothing was promoted:** open **Overview**, pick a healthy same-datacenter **failover** replica, and press **Promote** (`POST …/managed/members/:memberId/promote`). Manual promotion continues even when the old primary cannot be reached (the old member is marked **needs resync** afterward). That is separate from engine-dead automatic failover on a **live** server, which stops the old primary first and records `unfenced` when that stop cannot be confirmed.

Non-force **Promote** always asks the replica's daemon for a fresh health read first; the gate then requires `streaming`, lag within 64 MiB and 30 seconds on that reading, and (for MySQL and MariaDB) `fullyApplied === true`, or (for PostgreSQL) replay within 16 KiB of received WAL. If that refuses, the app offers **Promote anyway** — API `{ "force": true }` on the same route. **Force** skips those lag and health checks (never replica class) and accepts possible data loss if the old primary still had unreplicated commits. Copy on the sheet: _Promote anyway accepts possible data loss if the primary still has unreplicated commits._

### Backups from before the failover

Each backup file lives on the server that ran the primary when the backup was taken (the API exposes that host as `storedOnServerId` on each backup row). After promotion the primary moves; restore always targets the **current** primary's server.

**What you see:** **Restore** answers **409** `backup_on_other_server` — the response names the server that stored the file (the primary when the backup ran), says it can only be restored there, and tells you to take a new backup on the current primary or switch back first. No restore is enqueued.

**What to do:** run **Back up now** on the new primary, then restore from that backup if you need a point-in-time copy on the new writer.

### Short write outages and listener reloads

**Switchover or engine-dead automatic failover:** the shared listener drains the old primary, stops it, promotes the replica, and repoints ProxySQL. **Host-loss automatic failover** skips drain/stop on the silent host (attested fence) but still promotes and repoints listeners on connected servers. Read-write clients should expect a short gap — connection refused, timeout, or driver errors. Use connection retry/backoff; the host and port in the connection string stay the same.

**Adding a replica** (or changing who serves reads) enqueues `managed.ingress.reconcile` on every server that fronts the cluster so ProxySQL picks up the new backend. While that reconcile runs, read-write logins can see brief connection or write errors. Retry for a few seconds; a fresh ProxySQL stack can take a few seconds before its admin port answers.

### External access and the listener

With **Allow external access** off, SQL listeners are on `127.0.0.1` only (`15432` / `13306`). With it on, the same ports publish on all host addresses (`0.0.0.0`). Failover does not move the endpoint your apps dial — only which backend ProxySQL treats as the writer. The per-server switch and API are under [External access](#external-access) below.

### MariaDB 11.8 vs 12.3

**MariaDB 11.8** is the default series and supports failover replicas. **MariaDB 12.3** is creatable on **one server only** (`failoverCapable: false` in the release catalog): **Add replica** and **Convert to failover** are refused until failover tooling can read the series' `read_only` values. Existing 12.3 databases keep running; plan HA on 11.8 for new pairs.

### Orchestrator login and datacenter placement

MySQL and MariaDB automatic failover uses **Orchestrator** (one stack per organization on servers that host HA members). Two credentials are organization-wide, not Linux accounts:

- A **topology database login** — one derived MySQL user every HA cluster in the organization accepts so Orchestrator can register all members.
- **Orchestrator HTTP basic auth and a Raft token** — shared by every Raft peer in the org.

Raft voters are chosen **inside one datacenter** (`selectHaRaftMembers`): both servers in a failover pair must sit in the **same datacenter** so they share one Raft group. Postgres HA does not use Orchestrator; engine-dead reports on a live server use the Postgres probe instead.

### ProxySQL and 4 KiB kernel pages

Shared ProxySQL aborts on hosts whose kernel uses 16 KiB or 64 KiB pages (common on Raspberry Pi 5 until switched). Consumer servers need the proxy too — apps reach databases through `127.0.0.1:15432` / `13306` even when no engine runs there.

**What to do:** switch the Pi to the 4 KiB kernel before enrolling it — [Raspberry Pi and databases](/docs/using/raspberry-pi-and-databases).

## Backups

**Backups** tab, for all three engines. A backup is a logical dump of one database, stored on the server that runs the cluster's primary.

| Engine         | Dump                                  | File    |
| -------------- | ------------------------------------- | ------- |
| PostgreSQL     | `pg_dump` custom format, per database | `.dump` |
| MySQL, MariaDB | `mysqldump`, per database             | `.sql`  |

### Back up now, restore, delete

| Action          | What happens                                                                                                                                |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Back up now** | Dumps the database on the primary's server and records it in the list.                                                                      |
| **Restore**     | Typed confirmation (the cluster's name). Restores that backup into the cluster in place. A backup made by a schedule restores the same way. |
| **Delete**      | Two presses. Removes the backup.                                                                                                            |

Each backup is checked with a SHA-256 checksum when it is written and again before a restore; a restore refuses a file that no longer matches. Backups are metadata in the app: there is no download, and the file lives on the server (under `/backup`, or the directory the operator set with `TURBOPANEL_BACKUP_DIR`). **Manual backups to keep** in the cluster's settings (`1`–`50`) prunes the backups made with **Back up now**; each schedule keeps its own count.

### Schedules

The **Schedules** panel on the Backups tab makes backups on a timetable. Only organization **owners** and **managers** see it. The server runs them on its own, even while the control plane is unreachable, and a run that was missed because the server was off happens once when it is back.

Every **new** managed database starts with one schedule named **Daily**: every day at 03:MM server time (the minute is spread per database so databases on one server do not all start together), keeping the most recent `7`. It carries an **Automatic** badge. Databases that existed before schedules were added do not get one; add a schedule to those yourself.

<Steps>
  <Step>
    **Add schedule**, give it a **Name** (up to 64 characters) and choose
    **Schedule**: **Hourly**, **Daily** (a time, `HH:MM`, 24-hour), **Weekly**
    (a day and a time) or **Advanced: cron** (five fields: minute, hour, day of
    month, month, day of week).
  </Step>
  <Step>
    Pick a **Timezone** or leave **Server time** to follow the server's own
    clock.
  </Step>
  <Step>
    Set **Backups to keep** (`1`–`50`) and leave **Enabled** on. **Add
    schedule** saves it.
  </Step>
</Steps>

Each row shows the schedule in words (for example _Daily at 03:12_), how many it keeps, when it runs next, and the last run (_Succeeded_ or _Failed_, with the error). **Enabled** / paused switches it off without losing it, **Edit** changes it, **Run history** lists recent runs (newest first), and **Delete** removes the schedule and stops its timer: **backups it already made stay on the server**.

What to know:

- A schedule's count prunes **only that schedule's own** backups, so an hourly schedule keeping 24 never removes a daily schedule's backups or a manual one. Each schedule's files live in their own folder on the server.
- A database can have at most **20** schedules.
- A schedule that cannot run on the server is refused when you save it: `@reboot`, a cron line that fixes both a day of the month and a day of the week (cron would treat that as either, which is rarely what you mean), and a step in the day-of-week field such as every other Tuesday.
- After a save the app says when the server could not be reached; it picks the change up when it reconnects.
- A run is refused (and recorded as failed) when another backup or restore of the same cluster is running, or when the server is short of disk space (less than twice the previous backup's size, and never under 256 MiB).
- Backups stay on the server's own disk: they do not protect against losing the whole server. Offsite storage is not built yet.
- Schedules for **storage volumes** are separate and API-only today: see [Storage and variables](/docs/using/storage-and-variables#volume-backups).

## External access

One setting, per server: **Allow external access to the databases on this server**. The default is **No**.

A server runs one listener for every database on it, so who can reach it from outside is a fact about the server, not about one database.

| Setting          | Who can connect                                                                                                                                                                                                                                                                                           |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No** (default) | Only services on that server: sites run by a site owner's Linux user (they connect to `127.0.0.1` on port `13306` for MySQL and MariaDB, `15432` for PostgreSQL), and containers bound to the database over the organization's managed Docker network. Nothing off the machine can connect.               |
| **Yes**          | The same ports are also published on all of the server's addresses. Anyone who can reach the server's network can try to connect. TurboPanel's firewall is a preview only and enforces nothing yet, so restrict access with your cloud or provider firewall. It covers **every** database on that server. |

Find the switch in the **create database** form (it shows the chosen server's current value and warns when other databases already run there), in the database's **Settings** tab (one row per server that serves it, with how many other databases share it), and over the API at `GET`/`PUT /api/client/v1/servers/{id}/managed-external-access` (organization owners and managers). Saving tells the server at once; if the server is offline or the change cannot be delivered yet, it is saved and retried automatically, and the app shows it as waiting for the server. The **Connect** tab always lists the way in from this server only, and adds a way in from outside the server only while the setting is **Yes** (and the server has a public address or hostname).

## Lifecycle and organization settings

- **Start / Stop / Restart** act on the containers; stop keeps everything. **Apply** re-converges the cluster after a settings change.
- **Destroy** removes the cluster and its data; a project or environment holding a live cluster cannot be deleted until it is destroyed (`managed_runtime_present`).
- **Managed → Settings** (organization-wide): the default SSL mode, and the listener ports per engine family (`1024–65535`; `6032`, `6132` and `45000–45999` are reserved). Blank = platform default. A port conflict on a host is only detectable when the listener is applied.
