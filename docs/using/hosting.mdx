# Hosting — hostnames, ports and TLS

A service that runs is not yet a service anyone can reach. **Hosting** is the part of an environment that says how the outside world gets in: which hostnames answer, on which network face of the server, over which certificate, and — for a database or a game server — which TCP or UDP ports are published. This chapter covers the **Hosting** tab, the organization's certificate library under **Organization settings › Domains & certificates** (also reachable as **Servers › TLS**), and the Let's Encrypt path that runs through both. For a step-by-step walk from a new domain to a trusted certificate, read [Certificates](/docs/using/certificates).

## The model

Every server that serves hostnames runs TurboPanel's web server on ports 80 and 443, next to a port forwarder that carries raw TCP and UDP. A **hosting row** is one entry TurboPanel writes into that web server's configuration: a set of hostnames (or a set of ports), a service and target port behind them, a bind scope, and the certificate to serve.

Hosting rows come from two places, and which one owns a row decides where you edit it:

- **The Hosting tab** — rows you add by hand for a service. Edit and delete them there.
- **The compose document** — rows declared under `x-turbopanel.hosting[]` on a service. The platform materializes them on every deploy; on the Hosting tab they are shown read-only, captioned as compose-owned, and any change goes in the document. Trying to edit one through the API is refused with `hosting_owned_by_compose`.

Three rules hold everywhere:

1. **A hostname is unique within the organization.** Two hosting rows in one organization can never claim the same hostname, even on different paths; the database enforces it, not just the form.
2. **The certificate is a pin, not a copy.** A hosting row points at a certificate in the organization's TLS library (`tlsId`). No pin means a self-signed certificate made by the server's web server — fine for a private hostname, wrong for a public one, because browsers warn visitors about it.
3. **The Organization CA never issues hosting certificates.** It signs the platform's internal traffic (daemon, managed-database ingress). Public hostnames get an uploaded certificate, a self-signed one, or Let's Encrypt.

### Bind scopes

| Scope | The hostname answers on | Use it for |
| --- | --- | --- |
| `public` | Every interface — or one specific public IP when a **public IP** is picked from the organization's registry | Anything reachable from the internet. The only scope that can obtain a Let's Encrypt certificate. |
| `datacenter` | The server's datacenter address only | A service other servers in the same datacenter reach, never the internet. Needs the server to have a datacenter address (`datacenter_ip_required` at deploy otherwise). |
| `local` | `127.0.0.1` | A service only that host itself talks to. |

The bind is frozen into the server's web server configuration at deploy time, so changing it — or a member address moving — leaves the environment marked *needs redeploy* until you deploy again.

## Before you begin

- A deployed (or at least placed) environment — hosting rows attach to a service in one.
- For a public hostname: DNS for it pointing at the serving server's public address.
- For Let's Encrypt: an organization owner or manager has turned on **Allow Let's Encrypt certificates** under **Organization settings › Domains & certificates**, the hostname's bind is `public`, and ports 80 and 443 on that server are reachable from the internet.
- For a published TCP/UDP port: nothing else on that server already publishes the same port.

## Add a hostname

<Steps>
  <Step>
    Open the environment's **Hosting** tab. Below the server pin, each service has a hosting section; add a row under the service that should answer.
  </Step>
  <Step>
    Enter the **Hostnames** — one or more, each a full DNS name (no wildcards). Leave **Protocol** at *Http*.
  </Step>
  <Step>
    Pick the **bind**: `public`, `datacenter` or `local`. For `public`, optionally pick a **public IP** from the organization's registry to bind only that address; the IP must itself be registered with scope *public* (`hosting_bind_scope_mismatch` otherwise).
  </Step>
  <Step>
    Set the **Target port** the service listens on inside its container, and an optional **Path prefix** if only a sub-path of the hostname belongs to this service (with **Strip prefix** to remove it before forwarding).
  </Step>
  <Step>
    Choose the **TLS certificate**: leave it on **Self-signed**, pick a row from the library, or tick **Get a free Let's Encrypt certificate when I save**. The library only offers rows whose names cover every hostname on the row. See [Certificates](/docs/using/certificates) for what happens after you save.
  </Step>
  <Step>
    Toggle **Force HTTPS**, **Gzip** and **Brotli** as needed, then save. The hostname is live on the next deploy.
  </Step>
</Steps>

### Hosting variables and PHP options

Once a row is saved, it carries its own **Variables** panel — the hosting scope of the variable cascade, for values that differ per hostname (a `SITE_URL`, a per-host feature flag). For a site served by a host engine, the row also exposes **PHP** options: series (`8.3`, `8.4`), the [PHP mode](/docs/using/php), `memory_limit`, `max_execution_time`, and up to 64 static environment entries (`web.env`) of at most 4096 characters each.

### WordPress sites

After each deploy the daemon looks in a site's document root for the file names a WordPress install has (`wp-config.php`, or `wp-config-sample.php` beside `wp-settings.php`, together with `wp-includes/` or `wp-content/`) and reports the result. It reads file names only and never opens `wp-config.php`, so no password is read. The site then carries a **WordPress** tag on the **Services** tab, the Overview diagram and the phone Stack list; the tag clears on a later deploy if the files are gone. A plain PHP or static site gets no tag.

WordPress runs only on **MySQL or MariaDB**. The Services tab warns **WordPress needs MySQL or MariaDB** when the site is bound to a Postgres database ("Bind a MySQL or MariaDB database instead") or to no database at all ("Bind one, unless the site already points at a database elsewhere"). The second case is a check, not a verdict: a database the platform does not manage cannot be seen. Bind a [managed MySQL or MariaDB database](/docs/using/managed-databases) to the site to clear the warning.

## Publish a TCP or UDP port

<Steps>
  <Step>
    Add a hosting row under the service and set **Protocol** to *Tcp* or *Udp*. The hostnames field is replaced by **Ports**.
  </Step>
  <Step>
    Enter up to 10 mappings as `published:target` (or just `published` when both sides match). Each published port must be unique on the row; the same port published by another service on the same server is refused at deploy (`host_port_conflict`).
  </Step>
  <Step>
    Pick the bind scope as for a hostname, and save. The port forwarder publishes the port on the next deploy; TLS options do not apply.
  </Step>
</Steps>

## The TLS library

**Organization settings › Domains & certificates** (also **Servers › TLS**) is the organization's certificate library. Every row has a **source** and a **status**:

| Source | What it is | Who renews it |
| --- | --- | --- |
| `upload` | A certificate and private key you paste as PEM | You — upload a new row before it expires and re-pin |
| `self_signed` | A certificate the platform mints for the hostnames you list (RSA-2048, about 90 days) | You, by minting again |
| `lets_encrypt` | The hostnames to get a free Let's Encrypt certificate for. A new row holds no certificate or key. Once the web server on a serving server has the certificate, TurboPanel keeps an encrypted copy of the chain and its private key on the row (see [Stored copy](#stored-copy)). | The web server on each serving server, automatically |
| `organization_ca` | The organization's internal CA. Platform-managed; not pinnable to a hosting | The platform's renewal sweep |

| Status | Meaning |
| --- | --- |
| `ready` | Material present and valid; pinnable. |
| `pending` | Requested, material not yet present. |
| `automatic` | A Let's Encrypt row: the web server on the serving server gets and renews the certificate — pinnable. The library shows it as *Issued and renewed by the serving host*. The server also sends TurboPanel a copy of each certificate and its key, kept encrypted (see [Stored copy](#stored-copy)). |
| `expired` | Past its expiry date. Replace and re-pin. |
| `failed` | Issuance or import failed; see the row's message. |
| `revoked` | Retired by you. Pins fall back to a self-signed certificate on the next deploy. |

### Upload a certificate

<Steps>
  <Step>**Domains & certificates → Add certificate**, source *Uploaded*.</Step>
  <Step>Paste the **Certificate PEM** (the leaf first, then any intermediates) and the **Private key PEM**. An optional **Display name** labels the row.</Step>
  <Step>Save. The platform reads the names off the certificate; a certificate already in the library is refused with `tls_fingerprint_conflict`.</Step>
  <Step>On the environment's Hosting tab, pin the row on each hosting it should serve, and deploy.</Step>
</Steps>

### Mint a self-signed certificate

Source *Self-signed*, list the **Hostnames**, save. Useful for a `datacenter` or `local` hostname, or as a placeholder before a real certificate exists.

### Let's Encrypt for one domain

The quickest route to a trusted certificate is on the domain itself. Each web domain in an environment shows its **Certificate** state, and when Let's Encrypt is allowed for the organization it offers **Use Let's Encrypt**. TurboPanel checks DNS first, so a request is never sent to Let's Encrypt for a name that does not point at your server yet. That matters because every failed check at Let's Encrypt counts against its limit of 5 failed tries per name per hour; TurboPanel's own DNS check does not count. [Certificates](/docs/using/certificates) walks through the whole path, with every state and its fix.

<Steps>
  <Step>
    An organization owner or manager turns on **Allow Let's Encrypt certificates** under **Organization settings › Domains & certificates** (see [Let's Encrypt](#lets-encrypt) below). Without it the button is not shown.
  </Step>
  <Step>
    Open the environment's **Hosting** tab and find the domain. The **Certificate** block under it shows its state.
  </Step>
  <Step>
    Optionally choose what happens to the **www** name, then press **Use Let's Encrypt** (or tick **Get a free Let's Encrypt certificate when I save** while adding the domain). The domain must be on a `public` bind and be a name Let's Encrypt can reach: no wildcard, IP address or private name.
  </Step>
  <Step>
    If every name already points at the server, the certificate is pinned at once. If the environment is already deployed, TurboPanel sends only the domain change to its servers, with no build and no restart, and the block reads **Getting a certificate** while the server's web server asks Let's Encrypt. It can do that only when every server is online and up to date, no deploy is running, and nothing else in the environment has changed since its last deploy. Otherwise the block says **Deploy this environment to start it** and offers **Deploy now**: the certificate is requested during that deploy. After that the web server renews it on its own.
  </Step>
  <Step>
    If a name does not point at the server yet, nothing is pinned and the block reads **Waiting for DNS**, with the result per name and the address to point at. **Check DNS** repeats the check. TurboPanel also checks again every few minutes, pins the certificate as soon as DNS is right and sends it to the servers the same way as above. It gives up on a request after 7 days; the block then shows **Self-signed certificate** again and you press **Use Let's Encrypt** once DNS is fixed.
  </Step>
</Steps>

The state of the **Certificate** block is decided by the control plane, not guessed by the app:

| State | What the block says | What to do |
| --- | --- | --- |
| **Self-signed certificate** | Browsers will warn visitors. | Press **Use Let's Encrypt**, or pin an uploaded certificate. |
| **Uploaded certificate** | Days left, and that you renew this one. A warning shows at 14, 3 and 1 days, and once it has run out. | Upload a new certificate and pin it. |
| **Waiting for DNS** | Let's Encrypt starts as soon as the domain points at your server. | Fix the records named in the block, then **Check DNS**. |
| **Getting a certificate** | *This usually takes a minute or two*, or *Deploy this environment to start it. The certificate is requested during the deploy.* | Wait, or press **Deploy now**. |
| **Secure** | Let's Encrypt, renews automatically, with the days left. | Nothing. |
| **Renewal failed**, or **Couldn't get a certificate** if none was ever issued | The reason line from the server. Visitors see a warning when the current certificate runs out. | **Check DNS**, fix what it names, then **Try again**. |

A domain declared in the compose document (`x-turbopanel.hosting[]`) has its certificate set there too, so the block explains that and offers no button. This includes the hostname typed under **Visitors reach it at** on the **Set up production** screen of a new project, which is written into the environment's compose. Compose's own `tls.mode: automatic` is not supported yet and is refused at deploy; a fix is in progress. Until then, add a Let's Encrypt certificate for the exact hostname in the library ([below](#lets-encrypt)), pick it in that route's **TLS certificate** picker on the **Hosting** tab (this writes `tls.mode: certificate` with `certificateRef`), and deploy. This route skips the DNS check, and it always needs that deploy.

The same two actions are in the API, both needing **Manage** on the organization:

| Call | What it does |
| --- | --- |
| `PUT /hostings/:id/use-letsencrypt` | The button. Any body is ignored: the www choice saved on the hosting decides the names. Answers with the hosting, its `certificate` block (with the DNS report) and `needsDeploy`, which is `true` when the pinned certificate could not be sent to the servers without a deploy. Recorded in the audit log as `hosting.letsencrypt.requested`. |
| `GET /hostings/:id/dns-check` | The same DNS check, read-only: each name, the addresses it resolves to and the address it should resolve to. |

`GET /hostings` and `GET /hostings/:id` carry the `certificate` block: `state` (`test_certificate`, `uploaded`, `secure`, `waiting_for_dns`, `issuing`, `renewal_failed`), the source, expiry and days left, whether it renews automatically, `lastError`, `lastIssuedAt`, the DNS report, and `needsDeploy`. Where Let's Encrypt has reported when a certificate was issued and when it runs out, the block shows both; until it has, a pinned certificate reads *Getting a certificate*.

### Let's Encrypt

Let's Encrypt is **off by default for every organization**. Some operators do not want the platform contacting a public CA on their servers' behalf at all, so it is an explicit opt-in, and turning it back off is immediate: no new certificate can be requested, and a deploy that still pins a Let's Encrypt (`automatic`) row is refused with `acme_requires_org_opt_in` until you turn the opt-in back on or pin another certificate. Certificates the servers already have are not revoked; they stay on the server. The encrypted copies of their keys that TurboPanel stores are erased, because nothing needs them any more.

<Steps>
  <Step>
    **Organization settings › Domains & certificates**, turn on **Allow Let's Encrypt certificates**. Until this is on, the *Let's Encrypt* source is disabled in **Add certificate** and the API refuses with `lets_encrypt_not_enabled`.
  </Step>
  <Step>
    **Add certificate**, source *Let's Encrypt*, list the exact **Hostnames** — no wildcards (`wildcard_unsupported`), and only the port-80 check (HTTP-01) is supported (`dns_01_unsupported`). The row is created with status `automatic`. This form does not check DNS.
  </Step>
  <Step>
    Make sure each hostname resolves to the serving server and that ports 80 and 443 on it are open to the internet.
  </Step>
  <Step>
    On the Hosting tab, set the hosting's bind to `public` and pick the row in its **TLS certificate** picker. Deploy: picking a library row does not send anything to the servers by itself. The server's web server asks Let's Encrypt for the certificate during that deploy and renews it on its own. Once it has the certificate, TurboPanel keeps an encrypted copy of it and its key (see [Stored copy](#stored-copy)).
  </Step>
</Steps>

If issuance fails — a hostname that does not resolve, a closed port 80, a Let's Encrypt rate limit — the daemon notices within a minute or two and the row shows **Issuance failing** with the reason; the deploy itself is not affected, and the hosting keeps serving a self-signed certificate until issuance succeeds.

### Stored copy

The web server on the server that serves the domain gets the certificate and renews it. Once it has one, that server's daemon sends the panel a copy of the certificate chain and its private key (one hostname at a time, over the daemon's connection to the control plane). The panel checks the pair — it covers the domain, has not expired, the key belongs to the certificate, and the domain is one of the sites placed on that server — then keeps the key encrypted with the panel's secret, the same way as an uploaded certificate's key. The same step records the real start date, expiry, issuer, subject and fingerprint, so the certificate list shows them instead of waiting for a probe.

- **The key is never shown or returned.** No page or API call returns it; the certificate list and the API carry only the public chain. The key leaves the panel's database only sealed: in a deploy it travels encrypted so that only the daemon of the server receiving the deploy can open it, and database backups hold it encrypted like every other sealed value.
- **A newer certificate replaces the copy; an older one never does.** Each new certificate the web server gets is sent the same way. The panel replaces the stored pair only when the new certificate expires later. A certificate that expires earlier, or on the same day as the stored one, is ignored, so an old pair sent again cannot overwrite a newer one. A certificate for a different name of the same entry (the web server gets a separate certificate for each name) is also ignored while the stored one is still valid.
- **Delete a domain and the copy waits at least 30 days.** The panel's scheduled sweep notices when no domain pins a Let's Encrypt certificate any more and starts a 30-day clock from that moment, so adding the site back in that time finds it. After that the sweep deletes the certificate row and its key. The sweep runs on the panel's regular schedule, so the exact day can be later than 30 days after the domain was removed. The sweep only looks at Let's Encrypt entries that are still `automatic`; a revoked entry is not swept, because its key was already erased when it was revoked.
- **Revoke a Let's Encrypt certificate, or turn Let's Encrypt off for the organization, and the stored key and chain are erased as part of that change.** The row stays. Deleting the certificate removes the row and its key. Copies already inside earlier database backups are not touched.
- **The panel's secret protects the copies.** They use the same encryption as uploaded certificate keys, so the re-encryption step that follows a secret rotation covers them too. Keep the secret apart from database backups: a backup of the database alone holds only encrypted keys.

In a panel release that includes the matching interface change, the certificate list also says whether a copy is stored (with its issuer and start date) or that the host has not sent one yet. Using a stored copy to bring a site up on another server without asking Let's Encrypt again is planned for a later release; today a moved site gets a new certificate from the new server.

### Revoke and retire

**Revoke** on a library row sets it `revoked`; hostings pinned to it fall back to a self-signed certificate on their next deploy. There is no CRL or OCSP: a client that already holds the certificate keeps trusting it until it expires. The organization CA is retired and rotated as a whole, from its own panel — [Organization CA](/docs/security/organization-ca).

## Reference

### Hosting options

| Field | Values | Notes |
| --- | --- | --- |
| `hostnames[]` | Full DNS names | Required for `http`. Unique per organization. |
| `protocol` | `http` (default) · `tcp` · `udp` | `tcp`/`udp` replace hostnames with `ports`. |
| `ports[]` | `{ published, target }` | Required for `tcp`/`udp`; at most 10; `published` unique on the row; ports 1–65535. |
| `bind` | `public` · `datacenter` · `local` | See *Bind scopes*. |
| `ipId` | uuid | A registered public IP to bind; needs `bind: public` and an IP of scope `public`. |
| `tlsId` | uuid or unset | The library pin; unset = self-signed. Compose spells it `tls: { mode, certificateRef }`. |
| `targetPort` | 1–65535 | The container port. |
| `pathPrefix` | `/path` | Route only this prefix. |
| `proxy.forceHttps` · `proxy.gzip` · `proxy.brotli` · `proxy.stripPrefix` | boolean / string | The **Force HTTPS**, **Gzip**, **Brotli**, **Strip prefix** controls. |
| `web.env` | up to 64 keys (`[A-Za-z_]\w*`), values ≤ 4096 chars | Static environment for host-engine sites. |
| `web.php` | `version`, `memoryLimit`, `maxExecutionTime` | Site PHP options. |

### Compose spelling

The same row, declared on a service:

```yaml
x-turbopanel:
  hosting:
    - hostname: shop.example.com
      pathPrefix: /api
      targetPort: 3000
      forceHttps: true
      tls: { mode: certificate, certificateRef: shop-cert } # internal | certificate (+ certificateRef) | automatic
      bind: { scope: public, ipRef: edge } # public | datacenter | local
```

`internal` (the default) is a self-signed certificate. `certificate` pins a library certificate, which can be a Let's Encrypt row. `automatic` is recognised but not supported yet: it is refused at deploy with `hosting_tls_mode_unsupported` while a fix is in progress. `certificateRef` names a library certificate by its id or its display name; `ipRef` names a registered IP by its id or its address. An unknown reference is refused at deploy (`hosting_tls_ref_unresolved`, `hosting_ip_ref_unresolved`); the editor's linter flags it earlier when it knows the organization's library.

### Certificate lifetimes

| Certificate | Lifetime |
| --- | --- |
| Self-signed library certificate | ~90 days |
| Let's Encrypt | 90 days today; 64 days from 2027-02-10 and 45 days from 2028-02-16. Renewed automatically by the web server on the serving server |
| Organization CA leaves (internal) | 90 days, re-issued at a third remaining |
| Organization CA root | 3650 days |

## Errors

| Code | Status | Meaning | What to do |
| --- | --- | --- | --- |
| `hostname_in_use` | 409 | Another hosting in the organization already serves this hostname. | Find it under that project's Hosting tab; remove it or pick another name. |
| `hosting_owned_by_compose` | 409 | The row is declared in the compose document. | Edit `x-turbopanel.hosting[]` on the service instead. |
| `hosting_bind_scope_mismatch` | 400 | A public IP was picked with a non-public bind, or the IP's registered scope is not `public`. | Set `bind: public`, or pick an IP registered as public. |
| `invalid_hosting_options` | 400 | A field has the wrong shape (a bad port, a `tcp` row with no ports, more than 10 ports). | See the options table. |
| `lets_encrypt_not_enabled` | 403 | The organization has not opted in. | **Organization settings › Domains & certificates → Allow Let's Encrypt certificates**. |
| `hosting_not_http`, `hosting_has_no_hostnames` | 400 | **Use Let's Encrypt** on a hosting that is not a web (HTTP) hosting, or that has no hostnames yet. | Add a hostname to a web hosting first. |
| `letsencrypt_hostname_unsupported` | 400 | One of the domain's names is a wildcard, an IP address or a private name. | Use public names only, or another certificate. |
| `wildcard_unsupported`, `dns_01_unsupported` | 400 | A `*.` hostname, or a DNS-01 challenge, on a Let's Encrypt row. | List each hostname; HTTP-01 only. |
| `private_hostname_unsupported` | 400 | A loopback or private hostname on a Let's Encrypt row. | Use a public name, or a self-signed or Organization CA certificate. |
| `tls_fingerprint_conflict` | 409 | This certificate is already in the library. | Pin the existing row. |
| `organization_ca_exists`, `organization_ca_retire_required` | 409 | An organization CA already exists, or the current one must be retired before a new one is minted. | Use the Organization CA panel's rotate flow. |
| `acme_requires_public_bind` | 400 (deploy) | A Let's Encrypt row is pinned on a `datacenter` or `local` hosting. | Set the bind to `public`. |
| `acme_requires_org_opt_in` | 400 (deploy) | An `automatic` (Let's Encrypt) row is pinned but the organization's opt-in is off. | Turn the opt-in back on, or pin another certificate. |
| `hosting_tls_mode_unsupported` | 422 (deploy) | A compose route asks for `tls.mode: automatic`, which is not supported yet. | Use `certificate` with a `certificateRef` to a Let's Encrypt library row, or `internal`. |
| `tls_pin_not_found`, `tls_pin_mismatch`, `tls_pin_not_ready` | 400 (deploy) | The pinned row is gone, does not cover the hostnames, or is not `ready`/`automatic`. | Re-pin. |
| `hosting_route_conflict`, `hosting_hostname_conflict` | 409 (deploy) | Two rows in the environment claim the same hostname and path, or a compose-declared hostname collides with another hosting in the organization. | Change one of them. |
| `host_port_conflict` | 422 (deploy) | Two services on one server publish the same port. | Change the published port. |
| `datacenter_ip_required` | 422 (deploy) | A `datacenter` bind on a server with no datacenter address. | Add the server to a datacenter, or use `public`/`local`. |
